# PCネットワークモニター MVP仕様

## 1. 目的

Windows PCが現在使用しているインターネット接続について、OBS Browser Source上で次の情報を継続的に確認できるようにする。

- 使用中NICの接続状態とリンク速度
- 使用中NICの現在の送信・受信速度
- インターネットへの遅延
- 直近60秒の平均・最小・最大遅延
- 直近60秒のジッター
- ICMP利用時のパケット損失率
- HTTPフォールバック時のリクエスト失敗率
- 直近60秒の遅延推移
- 直近60秒の送受信速度推移
- 現在の連続測定失敗回数
- IPアドレスとホスト名を匿名化したTraceroute

本MVPでは測定値をそのまま提示し、回線品質の良否をアプリケーション側では判定しない。

## 2. 対象範囲

### 対象

- Windows
- ローカルPC上で動作する単一のモニタープロセス
- OBS Browser Sourceまたは通常のブラウザからの表示
- IPv4によるインターネット疎通監視
- 現在の経路に応じたNICの自動追従

### 対象外

- ONLINE / DEGRADED / OFFLINEなどの総合状態判定
- LAN内やデフォルトゲートウェイまでの品質測定
- 複数NICの同時表示
- 契約回線速度に対する帯域使用率、累積送受信量
- IPv6
- 測定結果の永続保存
- 外部サーバーへのテレメトリー送信

## 3. 既定設定

実行ファイルと同じディレクトリにある任意の `config.json` を起動時に1回読み込む。ファイルが存在しない場合は以下の既定値を使用する。

```json
{
  "icmpTarget": "8.8.8.8",
  "httpTarget": "https://www.google.com/generate_204",
  "traceroute": {
    "target": "",
    "intervalSeconds": 60,
    "maxNodes": 6
  }
}
```

設定ファイルでは片方の測定先だけを指定でき、省略した項目には既定値を使用する。明示的な空文字は省略とはみなさずエラーにする。

設定の再読み込みはMVPの対象外とする。設定値が不正な場合は既定値へ暗黙に戻さず、原因をログへ出力して起動を中止する。

### 検証ルール

- `icmpTarget`: IPv4アドレスまたはIPv4へ名前解決できるホスト名
- `httpTarget`: `https` URL
- `traceroute.target`: 空文字、IPv4アドレス、またはIPv4へ名前解決できるホスト名。空文字では `icmpTarget` を継承
- `traceroute.intervalSeconds`: 30以上3600以下
- `traceroute.maxNodes`: 3以上12以下
- 未知のJSONフィールド: エラー
- `icmpTarget` / `httpTarget` の空文字: エラー
- `traceroute.target` の空文字: `icmpTarget` の継承指定として有効

## 4. 使用中NICの選択

ICMP測定先へ到達するためにWindowsが選択する経路から、使用中NICを特定する。単純な「接続済みNICの先頭」ではなく、実際のルーティング結果を基準とする。

これにより、Ethernet / Wi-Fiの切り替えやVPN経路を反映する。経路とNIC情報は定期的に再評価し、変更時は表示へ自動反映する。

表示するNIC情報:

- NICの表示名
- 接続状態
- 送受信リンク速度
- インターフェース識別子
- 現在の送信速度と受信速度

リンク速度は実効スループットではなく、Windowsが報告するNICのリンク速度である。送信と受信で値が異なる場合はそれぞれ表示する。現在の送受信速度は、同じNICの累積オクテット数を1秒ごとに比較し、差分と実経過時間からbpsへ変換する。

初回取得、NIC変更、カウンター減少、NIC取得失敗、非接続状態では速度を値なしとする。NIC変更時は通信速度履歴をリセットし、異なるNICの値を混在させない。カウンター減少時は履歴を維持したまま新しい基準値を取り直し、次の有効な差分から測定を再開する。通信速度にはアプリ自身の測定通信を含む、使用中NIC全体の通信量が反映される。

WindowsネイティブAPIを利用し、PowerShellや外部コマンドの出力解析には依存しない。経路選択には `GetBestInterfaceEx`、NIC情報と統計カウンターの取得には `GetIfEntry2Ex` を使用する。

## 5. 測定方式

### 5.1 ICMP

通常はWindowsのICMP APIを使用し、1秒間隔でEcho Requestを1回送信する。管理者権限や `ping.exe` には依存しない。実装には `IcmpCreateFile` と同期型の `IcmpSendEcho` を使用し、各測定を1秒でタイムアウトさせる。

各測定は次を記録する。

- 測定方式
- 測定先
- 成否
- 成功時のRTT
- 測定時刻

### 5.2 HTTPフォールバック

ICMPが3回連続で失敗した場合、HTTP測定先へ確認リクエストを送る。

- HTTPが成功した場合: ICMPが利用できないと判断し、HTTP測定へ切り替える
- HTTPも失敗した場合: インターネット疎通失敗としてICMP測定の失敗に計上し、連続失敗カウンターをリセットする。次のHTTP確認は、新たにICMPが3回連続で失敗した後に行う
- HTTP測定中: 30秒ごとにICMPを再確認し、成功したらICMPへ戻す

HTTPの応答時間にはDNS、TCP、TLSおよびHTTPサーバーの処理時間が含まれるため、ICMP RTTと同一の値として比較しない。通常のWebダッシュボードには測定方式を表示する。

測定方式が切り替わったときは統計履歴をリセットし、異なる意味の測定値を同一集計へ混在させない。

### 5.3 Traceroute

TracerouteはWindows ICMP APIを使用し、TTLを1から最大30まで増やす。各ホップは1回、最大1秒で測定し、対象へ到達した時点で終了する。通常のICMP / HTTP測定とは別のgoroutineで順次実行し、前回の経路測定が完了してから既定60秒後に次を開始する。経路測定同士を重ねず、失敗しても通常測定とプロセスを停止しない。

経路データはプロセス内ではIPアドレスを保持できるが、WebSocketへはホップ番号、応答有無、RTT、直前の応答ホップからのRTT差、対象到達フラグだけを送る。IPアドレスとホスト名は配信しない。RTT差は応答なしを挟いだ場合は算出せず、各ホップのRTTを合計しない。

OBS表示は `LOCAL` と `TARGET` を必ず残し、その間を最大ノード数へ集約する。隣接する応答ホップ間でRTTが20 ms以上増えた箇所を遅延増加として優先し、連続する遅延増加はまとめられる。応答なしは経路障害の断定材料にせず `NO RESPONSE` と弱く表示し、対象へ到達しない場合は `ROUTE INCOMPLETE` とする。

## 6. 統計値

統計は現在の測定方式による直近60回（通常は約60秒）の測定結果から算出する。

### 遅延

直近の成功した測定のRTTをミリ秒で表示する。成功値がまだない場合は値なしとして表示する。

### 平均・最小・最大遅延

現在の測定方式による直近60回のうち、成功したRTTだけを対象に平均・最小・最大を算出する。成功値がない場合はすべて値なしとする。

### ジッター

時間的に連続した成功測定について、隣接RTTの絶対差の平均を使用する。

```text
jitter = sum(abs(rtt[i] - rtt[i-1])) / 有効な隣接ペア数
```

測定失敗を挟むサンプル同士は隣接ペアに含めない。有効なペアがない場合は値なしとして表示する。

### パケット損失率

ICMP測定時に表示する。

```text
packetLoss = 失敗したICMP測定数 / 全ICMP測定数 * 100
```

### HTTPリクエスト失敗率

HTTP測定時に表示する。これはパケット損失率ではないため、画面上のラベルを切り替える。

```text
requestFailure = 失敗したHTTP測定数 / 全HTTP測定数 * 100
```

### 連続失敗回数

現在の履歴末尾から連続する失敗測定の件数を表示する。最新測定が成功している場合は0とする。測定方式が切り替わり履歴がリセットされた場合は、新しい方式の履歴だけを数える。

## 7. データ収集と配信

測定はブラウザ接続ごとに開始せず、アプリケーション内の共有モニターが1系統だけ実行する。

共有モニターは次を担当する。

1. 使用中NICの再評価
2. ICMP / HTTP測定
3. 統計用60サンプルと左右の描画余白を含む65秒以上の履歴管理
4. NIC送受信速度と左右の描画余白を含む65秒以上の通信履歴管理
5. 統計値の計算
6. 最新スナップショットの生成
7. 独立周期でのTracerouteと匿名化

WebSocketクライアントは共有モニターの最新スナップショットを受信する。ブラウザ接続数が増えても外部への測定回数は増加しない。

スナップショットには少なくとも次を含める。

- NIC情報
- 測定方式と測定先
- 最新の遅延
- 平均・最小・最大遅延
- ジッター
- パケット損失率またはHTTP失敗率
- 連続失敗回数
- 現在のNIC送信・受信速度と左右の描画余白を含む65秒以上の履歴
- 左右の描画余白を含む65秒以上の時刻、成否、RTT
- スナップショット生成時刻
- 匿名化した経路状態とホップ情報

## 8. UI

OBS表示は透明なオーバーレイとし、背景、外枠、パネル、カード、全体タイトル、NIC名・状態・リンク速度、測定先、配信状態を表示しない。ルート `/` は通常ブラウザ向けの案内ページとし、OBS表示には使用しない。

OBS向け表示は `/latency`、`/traffic`、`/route` の3ページで構成する。`/latency` は遅延だけを480 x 270 px、`/traffic` はNIC通信量だけを480 x 210 px、`/route` は匿名化した経路を480 x 300 pxで表示する。複数を表示する場合は、OBSで独立したBrowser Sourceとして配置する。未知のパスは404を返す。

ルート `/` にはLocal Web Server、WebSocket接続、モニターデータ受信の状態、最終更新時刻、確認付きのアプリ終了ボタンを表示する。状態アイコンと文言は固定幅の列で開始位置を揃える。あわせて `/latency`、`/traffic`、`/route`、GitHubリポジトリ、READMEの使い方をURLが見える箇条書きで表示し、フッターにMIT Licenseへのリンク、`© 2026 hazuki3417`、制作者を表示する。

数値一覧とグラフは、`/latency` と `/traffic` でWebSocket接続を分割せず表示だけを `parts` クエリで切り替える。`parts=values` は数値のみ、`parts=graph` はグラフのみ、`parts=values,graph` または未指定は両方を表示する。有効な値がない場合は両方へフォールバックする。`/route` は経路全体を1つの表示単位とし、`parts` では分割しない。

各Browser Sourceは共通のWebSocketエンドポイント `/ws` へ個別に接続する。バックエンドのモニター、履歴、最新スナップショットは全接続で共有し、クライアント数によってICMP、HTTP、NICの測定回数を増やさない。WebSocketのJSON契約もページ間で共通とする。

静的UIは `web/latency/`、`web/traffic/`、`web/route/` にページ固有のHTML・エントリースクリプト・描画モジュールを配置する。WebSocket接続、表示オプション、Canvas描画、DOM更新、基礎スタイルは `web/shared/` に置き、必要なページから絶対パスで読み込む。ルート `/` は案内ページ固有のHTML、スクリプト、スタイルだけを読み込み、グラフ描画モジュールを読み込まない。外部パッケージやフロントエンドのビルド工程は追加しない。

表示項目:

- 現在の送信 / 受信速度
- 最新遅延
- ジッター
- パケット損失率またはHTTPリクエスト失敗率
- 直近60秒の小さな遅延折れ線グラフ
- 平均 / 最小 / 最大遅延と連続失敗回数
- 直近60秒の送受信速度グラフ
- 匿名化した経路の縦型タイムライン

OBS向け表示では、遅延統計を2列に整列し、各列内のラベル・値・単位を独立した3列として配置する。ラベルは左揃え、固定幅の値列は右揃え、固定幅の単位列は左揃えとし、単位の文字数による位置ずれを防ぐ。NIC通信量の現在値はグラフの直前に配置する。グラフはタイトル、サンプル数、過去・現在ラベル、データ待機中の中央テキストを表示せず、左側に上限・中間・0、右上に単位付き上限値を表示する。

グラフは高DPI対応Canvasへ描画し、測定点を通る単調3次補間による滑らかな曲線とする。バックエンドの約1秒の計測周期は変更せず、全グラフで共有する `requestAnimationFrame` ループを最大60fpsで実行する。数値は最新値を即時表示し、グラフだけを2秒遅延させた固定60秒として表示する。左右各2秒の非表示描画領域と1秒の時刻余裕を含む65秒以上の履歴、および境界直前の1点を時刻基準で保持し、右側では受信済みの後続サンプルまで曲線を確定してから固定表示範囲へ入れる。測定間隔が一時的に短くなっても時間範囲を優先し、安全上限を256件とする。描画時計は最初のスナップショットで初期化した後、単調増加するブラウザの時計だけで進め、通常のWebSocket受信では設定し直さない。前回の最新サンプルが新しい履歴に含まれない場合、または時刻が逆行した場合だけ再初期化する。各サンプルの `checkedAt` を基準に実測値を補間せずグラフ全体を滑らかに左へ移動させる。左側は目盛りに必要な28 pxだけを確保し、その直後の固定境界より右側へ曲線をクリップする。右側も固定境界より先を描画したうえで非表示にし、境界を示す縦線は描画しない。最新値の水平延長は行わない。測定失敗を0 msとして描画せず、欠損区間で曲線を分断する。

数値はWebSocketスナップショットの受信時だけ実測値へ即時更新し、フレーム単位の数値補間や変更時のアニメーションは行わない。同じ表示値の場合はDOMを更新しない。`parts=values` ではCanvas描画ループへ登録せず、`parts=graph` では非表示の数値DOMを更新しない。総合状態の文言や、閾値に基づく良否の色分けは行わない。

WebSocketが切断された場合は既存画面を消さず、配信状態は表示せずに2秒間隔で再接続し、再接続後は最新スナップショットへ更新する。

## 9. エラー処理

- 使用可能な経路またはNICがない場合、NICを未接続として表現し、プロセスは継続する
- 一時的な測定失敗でプロセスを終了しない
- Tracerouteのタイムアウト・不完全経路・一時エラーで通常測定を停止しない
- 設定不備は起動時エラーとする
- WebSocketクライアントの切断は測定処理へ影響させない
- 測定およびNIC取得のエラーは、継続運転を妨げない範囲でログへ記録する
- 配布版はWindows GUIサブシステムでビルドし、コンソールを表示しない
- エラーはexe隣接の `logs/error.log` だけへ遅延生成し、5 MiBで `error.previous.log` へ1世代ローテーションする
- 終了APIは同一のHost・Originと専用ヘッダーを持つPOSTだけを受け付け、計測とHTTPサーバーをgraceful shutdownする
- 起動時にブラウザを自動表示しない

## 10. テスト方針

Windows Quality Gateで少なくとも次を検証する。

- 設定ファイルなし、正常値、不正値
- 統計対象60サンプルと、短い測定間隔でも左右各2秒の余白を含む65秒以上を保つ描画バッファ
- NIC累積カウンターからの送受信速度計算
- 初回、NIC変更、カウンター減少、NIC取得失敗の処理
- 遅延、ジッター、損失率、失敗率の計算
- 平均・最小・最大遅延と連続失敗回数の計算
- ICMPからHTTP、HTTPからICMPへの状態遷移
- 測定方式切り替え時の履歴リセット
- TracerouteのTTL増加、対象到達時の停止、最大30ホップ、不完全経路
- 経路JSONにIPアドレス・ホスト名が含まれないこと
- 経路の最大ノード数、遅延増加・応答なし・不完全経路の表示
- WebSocketスナップショットのJSON形式
- Windows向け実行ファイルのビルド

Windows APIと外部通信はインターフェースで分離し、単体テストではテストダブルへ置き換えられる構造にする。

## 11. 受け入れ条件

1. Windowsで通常ユーザー権限のまま起動できる
2. 設定なしでGoogleを既定測定先として動作する
3. `config.json` でICMPとHTTPの測定先を変更できる
4. 現在の経路で使用されるNICを自動表示する
5. NICまたは経路の変更へ自動追従する
6. 1秒間隔で測定し、直近60回から統計を算出する
7. ICMPが利用できずHTTPは利用できる場合、自動的にHTTPへ切り替わる
8. HTTP測定中にICMPが回復した場合、自動的にICMPへ戻る
